# 精确技能引用类型补查工作流

这是开发流程，不是玩家版本或新增角色的发布凭据。查询只读取精确 Class/CDO
类型，不生成 Actor、不授予能力、不接管、不施法。联机仍暂缓。

## 输入与去重

- 输入来自已关闭、隔离核对通过的子树查询；只有完整成功的父能力提供引用。
- 保留真实 `AbilityToActivate` 对象路径、来源会话、父能力键与父能力类，不推导招式名。
- 同一批合并已闭合原生授予日志中的精确待查询类；保留角色、配置、来源会话及授予计数行。
  它们只提供查询来源，不取代新实例的授予或激活核验。同一类同时被子树和授予日志引用时
  只加载一次，两类来源都保留。授予来源的日志、会话及收尾证明摘要也一并冻结。
- 当前盘点中已确认的 leaf/subtree 不再补查；冲突、已拒绝查询、玩家上下文及未观察的
  NPC 资源目录保留为待审查项。拒绝不自动变成重试。
- `boss_subtree_inventory.py` 默认只冻结历史上未开始的精确父能力，最多 96 项。
  去重按资源目录身份及完整类路径进行，不依赖可能随元数据收据更新的 job key。
  成功、拒绝和原生中断都算已尝试；显式续查入口仍保留原冻结来源核验。

## 集中查询

1. 保留 Git 存档，通过 `research_scene_checkpoint.py prepare --acceptance --observed-ui`
   准备隔离研究会话。本人官方认证另走现有的限时登录入口；不在仅本机通信的会话中
   尝试在线认证，不自动化登录，不修改正式存档。
2. 用独立 computer-use 客户端观察研究 Steam 属性，完成原有云同步截图核对。
   启动研究版、选择“继续游戏”即可回到保存的溪谷场景。
3. 对里程碑返回的精确目录执行 `stage_boss_subtree_references.py stage <目录>`。
   装配前逐份归档原始源码，再检查所有权、空闲状态、离线隔离、PID、加载器及正式文件；
   归档后若会话、进程或完整查询与清理时间预算改变，不写入另一个研究会话。
4. 执行同一目录的 `reload-gate`。只有十秒有效门槛中的窗口、PID、批次及用途均匹配，
   才通过获准的窗口工具发送一次 Ctrl+R。门槛拒绝不发送按键。
5. 总 START、每个子批 START/结果/END、总 END 必须严格串行。仍在运行、STOP、重复、
   乱序、其他批次、孤立结果或 END 后再次出现同类事件，都不能捕获为通过。
6. 仍在空闲载体阶段时执行 `capture`。随后用 `ahua_practice.py stop` 关闭本轮，
   确认研究箱为空、加载器已撤除、正式文件及主机配置未变化，再执行：

   ```text
   stage_boss_subtree_references.py collect <原冻结目录> --session <原会话>
   ```

若需要其他独立元数据查询，应排在本收集器前面；其日志以各自装配时的字节偏移隔开。
不要在本收集器的 END 后追加同前缀查询，也不要重载已经开始的这批查询。
当前这 13 个精确授予待补查类已经合并，不再另外装配其原始批次，以免重复查询。

## 关闭后导入

关闭重放核对原始 manifest、脚本、装配 intent、staged、日志前缀、全部事件、capture
及收尾证明。历史验证使用本轮归档源码，不调用当前 `inputs()` 或重建计划，避免收据
导入后发生递归及旧队列被新清单替换。

独立收据写入 `research/boss-adaptation/subtree-reference-receipts/`；盘点只导入已重放的
类型结果。一个类确认为 leaf，不表示任何角色获得了它，也不表示它能独立播放、造成
伤害、连续使用、取消或跨图。因此仍需精确角色配置的原生授予核对及集中实机验收，
不能据此加入玩家角色列表。原始日志、存档及账号相关文件保持本机私有，不上传 Git。
